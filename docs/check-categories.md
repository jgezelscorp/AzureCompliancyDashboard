# Check categories (derived, versioned)

Real Azure guest-configuration baseline reports carry no category per check, so
without help every check would be "Uncategorized". The app therefore derives a
category from the check name with an ordered, versioned rule set.

**A derived category is an app heuristic. It is not source-backed, not certified
and not a mapping to any benchmark section.** It exists only to make long check
lists navigable.

## Single source of truth

`backend/app/domain/check_categories.json` holds `rulesVersion`, the default
category and the ordered rules (`id`, `category`, RE2-compatible `pattern`; first
match wins, so exceptions come first). It is used by:

- the backend (`backend/app/domain/categories.py`),
- the workbook queries, generated by `scripts/build_workbook.py` into a KQL
  `case()` (the `__CATEGORY_CASE(col)__` token), so the two cannot drift.

`tests/workbook/test_category_parity.py` parses the generated KQL back out of the
workbook and compares it with the Python categorizer on
`tests/golden/check-category-golden.json`.

## Taxonomy (rules v1)

Account Policies, Audit Policy, User Rights Assignment, Security Options,
Windows Firewall, Windows Defender / Exploit Protection, Credential / Platform
Protection, Services, Registry / Administrative Templates, Remote Desktop,
Event Log, and `Uncategorized` for anything unmatched. The names follow the
public Microsoft Windows security baseline groupings. Leading section numbers
such as `1.1.1` are mapped generically to a group; no benchmark text is shipped
and synthetic data stays labelled synthetic.

## Provenance

Each check carries `categorySource` and `categoryRuleVersion`:

| Source | Meaning |
|---|---|
| `source` | The report itself provided the category. |
| `derived` | Matched an app rule (UI: "Derived category (app rules v{n})"). |
| `override` | A configured override matched. |
| `unmapped` | No rule matched; stays `Uncategorized`. |

Precedence: override > source > derived > unmapped. Each check has exactly one
category, so category counts are never double counted.

## Versioning and recompute

Bump `rulesVersion` whenever a rule changes. Stored columns
(`checks.derived_category`, `category_source`, `category_rule_version`) are
refreshed by `recategorize_checks` at worker startup for rows with an older
version. Raw evidence (`checks.category`, status, reasons) is never modified.
The API resolves the effective category at read time, so it is always current.

## Overrides

The shared-settings RBAC gate (`ACD_AUTH_ANCHOR_*`) is not enabled in this
deployment, so overrides are configuration-managed instead of UI-edited:

- `ACD_CATEGORY_OVERRIDES`: inline JSON list, e.g.
  `[{"type":"prefix","pattern":"Audit Foo","category":"Audit Policy"}]`
- `ACD_CATEGORY_OVERRIDES_FILE`: path to a JSON file with the same shape
  (entries from the file are evaluated first).

`type` is `exact`, `prefix` or `regex`. Invalid entries fail validation at
startup. Overridden checks show source `override` in the UI.
Container Apps: set `categoryOverrides` in `infra/bicep/containerapps/main.bicep`
or `az containerapp update --set-env-vars`.

## Known limits

- Heuristic, not a benchmark mapping; a few items are approximate (for example
  anti-spoofing and PIN settings sit under Credential / Platform Protection).
- App-side overrides are not applied in the workbook (it uses the shared rules only).
- The Log Analytics `Category` column carries only source-backed categories; the
  workbook History tab derives the category from `CheckName` with the same rules.
- With ARG, the Categories tab is limited by the Kusto `case()` argument cap (30 rules enforced).
